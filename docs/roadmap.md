# 自主开发路线与当前边界

## 第一阶段：可测试的诊断基线

- [x] 独立 Kotlin / Compose 工程，不引入现成启动器或容器源码。
- [x] 指定包可见性、游戏版本和 base/split 结构检测。
- [x] ABI、实际内存页大小、内存和存储检测。
- [x] 明确标识的原版启动与手动反馈记录。
- [x] 系统文件选择器导出诊断。
- [x] ZIP 文本资源结构检查、内容哈希与事务式缓存。
- [x] 有界解压、路径验证、UTF-8 与 JSON 检查的核心测试。
- [ ] vivo V2458A Android 16 安装、界面、检测、原版启动与导出真机验证。

第一阶段 APK 是技术探针，尚未实现游戏内汉化。原版启动和包审计都是实际功能，但不能替代汉化接入验证。

## 第二阶段：确定游戏接入方式

根据真机报告固定游戏版本、安装来源、ABI、页大小、Unity 原生库和可访问安装结构。进一步验证官方客户端是否提供可用的本地化导入入口，以及资源下载和校验行为。

若缺少可用入口，单独评估自主容器的最小实现和兼容成本；不能通过启动器 UI 或普通存储权限假装已完成免 Root 汉化。也不将 Root 资源替换路线悄悄当作默认方案。

验收：在用户真机上，以明确记录的接入方式显示一段自行制作的中文测试文本，重启可复现。验证前不启用「启动汉化版」按钮。

## 第三阶段：汉化资源与显示

- 用结构化上下文配对译文，保持 ID、资源键和语音字段不变。
- 验证实际游戏版本、资源版本、文本格式和中文字体渲染。
- 加入补丁预备、原子启用、失败回滚与恢复原文。
- 缺失或无法可靠匹配的内容保留原文。
- 使用第三方译文前记录其来源与许可，程序原创不改变译文版权。

验收：主页、剧情、战斗技能说明可读，富文本和动态数值正确，失败时可以恢复。

## 第四阶段：更新与维护

分别管理游戏版本、汉化版本和启动器版本。验证一次真实游戏更新、一次补丁更新和一次同签名启动器升级，保持游戏资源与登录状态。

只声明支持实际通过验证的设备组合；游戏登录、后台恢复、16 KB 页设备和更多厂商系统分别记录测试结果。
